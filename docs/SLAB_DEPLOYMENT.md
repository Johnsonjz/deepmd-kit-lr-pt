# z-slab 分布式网格：在单卡极限体系（≈50 万原子）上是否值得部署

`midtown` 后端的 **z-slab 分布式求解**（`SOG_MIDTOWN_SLAB=1`，两转置 3D FFT + NCCL）此前
只在小体系上测过（12288 原子、97³ 网格），结论是**不值得部署**：慢 2.4×、每卡显存反而更费
（NCCL 固定吃 ~146 MiB/rank）。本文件把那次的结论放到**部署尺度的检验性实验**上重测。

> **一句话结论**
> 1. 在**单卡极限体系（50 万原子）**、按生产精度网格（668³，间距 0.25 Å）上，**slab np=4 的
>    单次调用时间与单卡 replicated 相同（82 / 84 ms，min）**，而每卡常驻显存只有
>    **3.14 GB vs 12.97 GB（4.1×）**。小体系上"又慢又费显存"的结论**在部署尺度上反转**。
> 2. 显存优势的来源不是 mesh 变小（那是 1/np，本来就有），而是**NCCL 的固定开销被摊薄**：
>    小网格上 146 MiB ≈ 200% 的账单，668³ 上 ≈ 4%。
> 3. **仍需 `processors 1 1 np`**。非 z 的进程网格走 `full_brick` 分支（正确，但 6–8× 慢、
>    2× 显存），见 §4。

## 1. 部署尺度：50 万原子

### 间距 0.25 Å（668³，生产精度网格）—— 主表

| 路径 | 时间 min (ms) | 时间 med (ms) | 每卡常驻显存 |
|---|---|---|---|
| replicated, np=1 | **83.7** | 94.1 | **12966 MiB** |
| slab, np=1 | 185.3 | 188.5 | 13062 MiB |
| slab, np=2 | 173.5 | 177.1 | 6762 MiB |
| slab, np=4 | **82.2** | 95.6 | **3142 MiB** |

### 间距 0.5 Å（334³，粗网格）—— 对照

| 路径 | 时间 min (ms) | 时间 med (ms) | 每卡常驻显存 |
|---|---|---|---|
| replicated, np=1 | **8.46** | 13.11 | **1480 MiB** |
| slab, np=1 | 40.05 | 46.56 | 1462 MiB |
| slab, np=2 | 31.62 | 32.70 | 930 MiB |
| slab, np=4 | 21.62 | 23.64 | 572 MiB |

**读法：**

- **网格越细，slab 的相对劣势越小。** 334³ 上 slab np=4 比单卡慢 1.8×（med 23.6 vs 13.1）；
  668³ 上**基本持平**（95.6 vs 94.1）。原因是：每 rank 的 FFT/绿函数工作量随
  `nx·ny·nz/np` 增长，而 NCCL 的固定延迟与每卡固定显存不随网格变。
- 由此可以外推 **部署尺度的拐点**：只要 mesh 在 ~500³ 以上，slab np=4 的时间就打平单卡，
  显存省 4×。生产网格在力精度 1e-4、σ_min=2.0 Å 下落在 **173³–513³**（122.31 Å 盒，
  见 `MIDTOWN_VS_BSPLINE_BENCH.md`）；50 万原子（167 Å 盒）对应的就是 **235³–700³**，
  即**整段都在拐点之上**。
- **np=1 的 slab 恒慢 ~2×**（185 vs 84）：它跑的是同一套两转置 FFT，却没有分摊任何工作。
  这是分派 bug 的哨兵——np=1 想快就**不要**开 slab。

### 每卡能装多少

按 668³、24 GB 卡（扣掉别人的、按 20 GB 可用）：

- replicated：12.97 GB / 50 万原子 → **≈77 万原子/卡**
- slab np=4：3.14 GB / 50 万原子 → **≈320 万原子/卡**（4 卡合计 ≈1280 万）

所以 slab 的实际价值不是"同样的体系跑得更快"，而是**同样的卡跑 4 倍的体系，或者在同样体系上
把 ~10 GB/卡 还给描述符**——后者正是 50 万原子成为单卡极限的原因。

## 2. 时间都去哪了（668³，np=4）

`SOG_SLAB_TIME=1`，稳态单次 78 ms（算子内），算子外 Python/打包 ~13 ms：

| 阶段 | ms |
|---|---|
| spread + 反向 halo | 6.6 |
| (x,y) FFT + 打包 | 5.4 |
| **forward all-to-all** | **15.1** |
| z FFT + 绿函数 + 逆 | 14.6 |
| 累加器 all-reduce | 4.0 |
| **inverse all-to-all** | **22.7** |
| 逆 (x,y) FFT + 散包 | 5.5 |
| 正向 halo | 2.4 |
| gather | 1.3 |
| **合计** | **78.3** |

四次 collective 合计 41.8 ms（54%），两次转置 37.8 ms（48%）。**转置是硬成本**：三维 FFT
在两个方向之间必须交换数据，复制路径一次都不用，这是它单卡更快、但显存 1/np 换不来的原因。
两条 all-to-all 不对称（15.1 vs 22.7）是流序造成的：反向 all-to-all 紧跟在累加器 all-reduce
之后，排在同一条 NCCL 流上。

## 3. 精度口径（不是本文件的重点，但必须一起读）

slab 与 replicated **共用同一套数值约定**（commit `eafd5ba1a`）：float32 网格、2⁻⁴⁰ 定点
spread、打包 `float2 (ge,gv)` 绿函数、半谱 R2C。三族样条对 replicated 的偏差：

| 样条 | max\|dF\| | 说明 |
|---|---|---|
| CubeS2-4/6（Form A/B）、QuadS-4/6 | ≤ 7.8e-6 | 与残差同量级（\|F\|rms ≈ 115） |
| B-spline-5 | 2.5e-5 | |
| B-spline-4/6 | ≤ 1.4e-4 | 两个**独立** float32 实现之间的地板 |

## 4. `full_brick` 分支（非 `1×1×np` 进程网格）

### 为什么需要

z-slab 的 mesh 按 **MPI rank = z 子域**切分，这只有在原子也按 z 分带时才正确
（LAMMPS 的 `processors 1 1 np`）。LAMMPS 默认的网格（比如 `2×2×1`、`1×2×2`）里
**每个 rank 的原子横跨整个盒子**，spread 会静默落到错误的 slab 上。原实现直接**拒绝**这种
分解（z 子域护栏），现在多了一条正确的路。

### 做什么

```
每个 rank：spread 到【整个 z 高度】的 brick（nz+2gh 层）
        → 自己的周期 ghost 在本地折叠
        → 一次设备内 all-reduce（uint64 定点，精确整数和）
        → 每 rank 都持有【全局密度】，只取自己的 ZL 层做两转置 FFT
        → 逆变换后各自只写了 ZL 层，其余被清零
        → 再一次 all-reduce（float 势场）→ 填周期 ghost
        → 从整高度 brick gather
```

转置、绿函数、能量/维里累加**一律不变**：每次 all-reduce 之后每 rank 的 ZL 层就是全局量，
与 z-band 路径逐字节同构。定点用 `ncclUint64`（数据类型 5），**整数求和的顺序无关**，
所以全局密度与原子分解/rank 数无关。

### 开关与验证

- `SOG_MIDTOWN_FULLBRICK=1` 强制；np=1 自动走这条路（`ZL == nz`）。
- 不设时，非 z 分解仍然报 z 子域护栏（已复测：`RuntimeError ... rank 1 owns atoms spanning
  z-grid [0.54, 35.9] but its slab is [18, 35]`）。

| 检验 | 结果 |
|---|---|
| 400 原子 18³、CubeS2/QuadS/B-spline、np=2/4（**按索引**切分，原子横跨全盒） | max\|dF\| 7.2e-6 / 6.6e-6 / 1.4e-4 |
| 35³ 网格（砖偏移 `zoff·nx·ny % 4 ≠ 0`，强制走 C2R 对齐 staging） | max\|dF\| 1.3e-5 |
| np=2 vs np=4 | **逐位相同（dF=0）** |
| 400 原子 18³ z-band，改造后回归 | 与改造前逐位相同 |

### 代价（50 万原子，np=4）

| | 时间 min (ms) | 每卡显存 |
|---|---|---|
| z-band 668³ | 82.2 | 3142 MiB |
| **full_brick** 668³ | **639.6** | **6128 MiB** |
| z-band 334³ | 21.6 | 572 MiB |
| **full_brick** 334³ | **99.0** | **956 MiB** |

贵在两次 all-reduce：668³ 的 uint64 密度砖是 **2.4 GB/rank**，按环算法每 rank 收发
1.5×，加浮点势场 1.2 GB → ~3.6 GB 过 PCIe，约 500 ms。参考实现用 reduce-scatter/all-gather
（一半流量）把它压到 ~一半，但 NCCL 的 reduce-scatter 要求**各 rank 等长**、而我们各 z 层的
宽度差 ≤1 层，所以这里用 all-reduce 换实现简单。**4090 无 NVLink，这条路径在 PCIe 上先天吃亏**；
有 NVLink 的机器上会好得多。

**取舍**：`full_brick` 是**任意进程网格的正确性兜底**，不是部署路径。能加
`processors 1 1 np` 就用 z-band。

## 5. 该不该开

| 场景 | 建议 |
|---|---|
| np=1 | **不要开**（恒慢 ~2×，显存无收益） |
| 多卡 + `processors 1 1 np` + mesh ≳500³ | **开**：时间打平单卡，显存 1/4 |
| 多卡 + 小 mesh（<300³） | 不开：collective 摊不薄，slab 更慢更费 |
| 多卡 + 非 z 进程网格 | 要么改 `processors 1 1 np`，要么接受 `full_brick` 的 6–8× 时间 |
| 单卡显存不够、又必须跑 | **开**（np=2/4）：这是它唯一能"救活"你的场景 |

默认仍**关闭**（`SOG_MIDTOWN_SLAB` 未设走 replicated）——它改变的是并行策略，应由输入决定，
而不是静默默认。

## 附：与 12288 原子结论的关系

12288 原子 / 97³ 上（历史、空闲机器）：replicated 0.227 ms / **68 MiB**，slab np=4
1.224 ms / **178 MiB**——**慢 2.4× 且更费显存**，结论"不值得"。同一套代码在
50 万原子 / 668³ 上是 **82 ms / 3142 MiB vs 84 ms / 12966 MiB**。差别不是代码变了，
是 **NCCL 的 ~146 MiB/rank 固定开销**在两种网格下的占比：97³ 上是 200%，668³ 上是 4%。
**结论依赖体系尺寸，那句话当时是对的，但不该外推到部署尺度。**
